# バックアップ

RapidWire はバックアップをサーバーの `backups` ボリュームにのみ保持する。
運営者は、通常は Web エクスプローラーの運営者ページ ([web.md](web.md#運営者用ページ)) から、`GET /v1/admin/backups` でそれを新しい順にページ単位で一覧表示し、`GET /v1/admin/backups/{name}` でダウンロードして ([api.md](api.md#運営者用バックアップ) を参照)、自分のマシンで検証または復元する。
[operations.md](operations.md#バックアップ) はバックアップのスケジュール、ダウンロード、復元について運営者が行う手順であり、この文書はジョブ、ファイル、検証を説明する。

## バックアップのジョブ

worker はジョブをスケジュールに従って実行し、`docker compose run --rm backup` は要求に応じて 1 回実行する。
どちらも `backup` のジョブのリースを保持するので 2 つの実行が重なることはなく、リースがほかで保持されている間、要求に応じたコマンドは "another backup is running" を出力して 1 で終了する。
要求に応じたコマンドは、両方のファイルを書き込めたときは 0、書き込めたがスナップショットが台帳の不変条件に違反するときは 4 (実行はそのこともエラーレベルでログに出す)、実行が失敗したかリースを失ったときは 1 で終了する。
worker は 60 秒ごとに実行の期限が来たかを確認する: 期限は、最新の完全な世代 (両方のファイルを持つもの) のファイルが書き込まれてから `RAPIDWIRE_BACKUP_INTERVAL_SECONDS` 後であり、完全な世代がなければただちにである。
失敗した実行はその時刻を動かさないので、定期の実行が失敗したか完了しなかった後、worker は次の試行まで 15 分待ち、リースがほかで保持されていることを見つけた確認はスキップされる。

1 回の実行は 1 つの UTC タイムスタンプを持つ 1 世代であり、`RAPIDWIRE_BACKUP_DIR` に 2 つのファイルを書き込む:

| ファイル | 内容 |
| --- | --- |
| `rapidwire-dump-<YYYYMMDDTHHMMSSZ>.sql.gz` | `mysqldump --single-transaction --hex-blob --no-tablespaces --set-gtid-purged=OFF --default-character-set=utf8mb4 --triggers --skip-routines --skip-events --quick <database>` を gzip 圧縮したもの。`CREATE DATABASE` 文も `USE` 文も持たないので、任意のデータベースに復元できる |
| `rapidwire-export-<YYYYMMDDTHHMMSSZ>.tar.gz` | 後述するアプリケーション形式のエクスポート |

- 各ファイルはバックアップディレクトリ内に `<name>.partial` として書き込まれ (エクスポートのテーブルファイルは隠しディレクトリ `.rapidwire-export-<timestamp>.staging` に置かれる)、同期され、最終的な名前に改名され、その後は決して変更されない。
- 実行はまず、中断された実行が残した途中のファイルとステージングディレクトリを削除する。ディレクトリ内のそれ以外の名前には決して触れない。
- エラーで終了した dump、標準エラーにエラーを報告した dump、mysqldump の完了コメントを欠く dump は失敗となり、行が自身のスナップショットの不変条件の値と食い違うエクスポートも失敗となる。
- 保持処理はすべての実行の後に動き、完全な世代だけを数える: 成功した実行は、自身を含めて最新の `RAPIDWIRE_BACKUP_RETENTION` 個の完全な世代を残し、それより古い世代のファイルをすべて削除する。一方、失敗した実行は完全な世代を 1 つも削除しない。
- 不完全な世代 (失敗した実行が残した、ファイルが 1 つだけのもの) のうち、保持処理が残すのは 1 つで、今回の実行の世代が不完全ならそれ、そうでなければ最新のもの (どの完全な世代よりも新しい場合に限る) であり、ほかは削除するので、ディレクトリが持つのは最大で `RAPIDWIRE_BACKUP_RETENTION` 個の完全な世代と 1 つの不完全な世代である。
- mysqldump は、ホスト、ポート、ユーザー、パスワードを、自身が読む唯一のオプションファイルとして、継承したパイプから受け取る (`--defaults-file=/dev/fd/N`)。そのため、パスワードがコマンドライン、環境変数、ファイルに現れることは決してなく、ログでは伏せられる。
- クライアントの環境からは、`MYSQL_TEST_LOGIN_FILE` を除くすべての `MYSQL*` と `LIBMYSQL*` の変数が取り除かれ、`MYSQL_TEST_LOGIN_FILE` には存在しないパスが設定される。そのため、`~/.my.cnf`、`~/.mylogin.cnf`、`MYSQL_HOST` や `MYSQL_PWD` などの変数のいずれもクライアントの接続や認証を差し替えられない。
- データベース名は、ASCII 英字、数字、`_` からなる 1 から 64 文字で、数字だけではない場合にのみクライアントに渡される。設定はそれ以外の `RAPIDWIRE_DB_NAME` を起動時に拒否する。

## エクスポート形式

アーカイブは最初のメンバーとして `manifest.json` を持ち、続いてスキーマのテーブルごとに 1 つの `tables/<table>.jsonl` ファイルをテーブル名の順に持つ。
すべてのテーブルは同じ一貫したスナップショットから主キーの順に読まれ、1 行に 1 つの JSON オブジェクトとして、キーをソートし、空白を入れず、ASCII エスケープを使って、保存されているすべての列を持つ (生成列は含まない)。

| 列の型 | エンコーディング |
| --- | --- |
| BIGINT、DECIMAL(38,0) | 10 進数の文字列。例えば `"-1269970084965912747"` |
| その他の整数 | JSON の数値 |
| Boolean | `true` または `false` |
| テキスト | 文字列 |
| DATETIME(6) | `"2026-10-31T03:00:00.000000Z"` (UTC、小数部は常に 6 桁) |
| BINARY、BLOB | 小文字の 16 進数の文字列 |
| JSON | ドキュメントを持つ要素 1 つの配列。そのため SQL の NULL (`null`) と JSON の null ドキュメント (`[null]`) は区別される |
| 任意の値 | SQL の NULL は `null` |

マニフェストは次を記録する:

```
{
  "format": "rapidwire-export",
  "format_version": 1,
  "app_version": "<rapidwire version that wrote the export>",
  "schema_revision": "<Alembic revision of the database>",
  "created_at": "2026-10-31T03:00:00.000000Z",
  "tables": [{"name", "file", "columns": [{"name", "encoding"}], "primary_key", "rows", "bytes", "sha256"}, ...],
  "invariants": {
    "currencies": [{"currency_id", "supply", "balance_sum", "stake_total"}, ...],
    "pools": [{"pool_id", "reserve_a", "reserve_b", "total_shares", "locked_shares", "provider_shares"}, ...],
    "verification": {"ok", "violations"}
  }
}
```

不変条件の値は、エクスポートのスナップショットに対して実行した台帳の不変条件の検証器から得る: 通貨の供給量はその発行勘定の残高の符号を反転したものであり、`balance_sum` (そのすべての残高の合計) は整合した台帳では `"0"` であり、`verification` は検証器の判定と違反の数である。

## ダウンロードの確認

`rapidwire backup verify FILE...` は RapidWire の設定もデータベースも必要としないので、パッケージをインストールした任意の環境から実行できる。

- エクスポートは先頭から末尾まで 1 回で読まれる: すべてのテーブルファイルがマニフェストの行数、サイズ、SHA-256 を持ち、すべての行がそのテーブルの正規の行であり、行が主キーの厳密な昇順に並び、アーカイブがマニフェストに載ったファイルだけを過不足なく安全なパスで持ち、行から再計算した不変条件の値がマニフェストの値と等しく、すべての通貨の残高の合計が 0 であり、マニフェストの検証結果に問題がないことが必要である。
- 不変条件の値の計算に使うテーブルや列をマニフェストが欠いているエクスポートや、それらの列を異なる方法でエンコードしているエクスポートは読めない。
- dump は完全に展開でき (これで gzip の CRC と長さが確認される)、mysqldump のヘッダーで始まり、その `-- Dump completed` コメントで終わらなければならない。

ファイルごとに 1 行 (`OK`、すべての問題を添えた `MISMATCH`、または `UNREADABLE`) を表示し、すべてのファイルが合格すれば 0、いずれかのファイルに不一致があれば 4、それ以外で読めないファイルがあれば 1 で終了する。

マニフェストには署名がない: `rapidwire backup verify` が検出するのは破損と内部の不整合であり、アーカイブ全体を別の整合したアーカイブに意図的に差し替えることは検出しない。
ダウンロードの真正性は API から得られ、その `X-Checksum-SHA256` を運営者ページと Python クライアントが受信したバイト列と照合する。

## 検証のための復元

`rapidwire backup restore --target-url mysql://user@host:port/database FILE` は、ローカルのコンテナなどの MySQL 8.4 サーバーの空のデータベースに 1 つのファイルを復元する。
そのようなサーバーを起動して復元するコマンドは [operations.md](operations.md#復元による検証) に示す。

- 復元先のデータベースは存在し、テーブルもストアドルーチンも持たないものでなければならない。コマンドはそれ以外を拒否する。
- パスワードは、URL にあればそこから (`mysql://user:password@host:port/db`、URL エスケープしたもの)、なければ `MYSQL_PWD` から取る。パスワードが表示されたりログに記録されたりすることは決してない。
- URL のデータベース名は、ASCII 英字、数字、`_` からなる 1 から 64 文字で、数字だけではない必要がある。
- dump は `mysql` クライアントに流し込まれる。クライアントは PATH 上になければならず (RapidWire のイメージには入っている)、パスワードの渡し方とほかのクライアント設定からの隔離は mysqldump と同じである。mysqldump のヘッダーで始まらないファイルはクライアントの起動前に拒否され、完了コメントのない dump は流し込んだ後で不一致として報告される。
- エクスポートは、データベースをマニフェストのスキーマのリビジョンまでマイグレーションし、マイグレーションが投入する行をエクスポートされた行で置き換え (読み込みの間は外部キーの確認を無効にする)、復元したテーブルを再びエクスポートすることで復元される: すべてのテーブルの行数、サイズ、SHA-256 と、不変条件の値がマニフェストと等しくなければならない。
- どちらの種類も、その後に復元したデータベースに対して台帳の不変条件の検証器を実行し、その数と違反を表示する。

コマンドは、復元が検証に通れば 0、チェックサムまたは不変条件の値の不一致、または不変条件違反があれば 4、復元そのものが失敗すれば 1 で終了する。
復元したエクスポートは AUTO_INCREMENT のカウンタを復元した最大の ID から続けるが、復元した dump はサーバーが持っていたカウンタを保つ。
